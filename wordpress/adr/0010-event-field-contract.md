# Event field generation and saved-value compatibility

## Design target

#229 covers `events_feed` and `schnuppertage`. The ACF discovery definitions,
generated Divi metadata, editor controls, import encoding and public decoding
must agree. Keep the current save/render seams and unrelated module schemas.

## Alternatives before implementation

| Approach | Interface and caller example | Tradeoffs |
| --- | --- | --- |
| A. Validate the current generator against hand-maintained metadata | `check_event_metadata(acf, native)`; call it after generating | Small change, but two field lists still disagree. Each new field needs two edits. |
| B. Complete the declarative ACF contract and check generated outputs | `build(components, check=False)`; `build(['events_feed', 'schnuppertage'], check=True)` | Existing consumers keep their interfaces. ACF becomes authoritative for discovery and types. Intentional incompatible changes need an explicit migration before removing a supported field. |
| C. Add an event value-codec adapter | `encode_event_values(values)`, `decode_event_values(attrs)`; import and render call the codec | Can describe new storage formats, but adds call sites and a second type definition beside the existing shared native adapter. It does not itself fix discovery drift. |

## Choice and depth evaluation

Choose B. Add the missing include-Schnuppertage toggle and event-type selector
to ACF, then generate only these families. The shared native field map remains
the runtime contract. Existing import, preview and rendering callers need no
new adapter. Compared with A, B requires stricter generation checks. Compared
with C, it gives up a dedicated versioned storage protocol that these unchanged
attributes do not need.

Generation prepares and validates all outputs before writing. Unsupported
event field types, duplicate/reserved names, removed fields and incompatible
types/choices fail with diagnostics. `--check` compares exact generated bytes
without creating directories or rewriting files. The PR conformance gate runs
the scoped event check. Other modules retain their current generation behavior.

## Compatibility rules

- An absent Divi field stays absent. Generation adds no saved defaults and does
  not rewrite existing posts. Public renderers retain their historical defaults.
- Explicit `false`, zero, empty text and empty lists retain their meaning.
  A zero event limit yields no results; WordPress must not replace it with a
  default page size. An omitted limit still uses three.
- Toggle values use the existing bool/`on`/`off` contract. Event types use the
  declared choices. An empty event type retains the historical Schnuppertag
  filter. A missing include toggle retains the general-only feed.
- Repeated list items retain their order and duplicates. No new row limit or
  truncation is introduced.
- Unknown saved attributes remain in the stored WordPress block. Extraction
  reads known fields only. An unknown value for a known selector is reported as
  invalid and renders no query, rather than becoming an unfiltered list. The
  existing migration refuses unknown/unsupported settings before writing.
- Defaults are fallbacks, not a materialized editor choice. The existing
  controls and public renderers still own their default presentation; ACF
  defaults do not get copied into saved Divi instances.

## Implementation and proof

1. Reproduce generator loss with a failing temporary-output equality test.
2. Complete ACF discovery and regenerate the two module metadata files.
3. Add read-only drift and compatibility checks, including refusal before writes.
4. Exercise the existing composer, WordPress parser, extraction, validation and
   public query with omitted, false, zero, empty, repeated and unknown values.
5. Save/reopen an unpublished copy through installed Divi and confirm query
   results with synthetic events. Keep previews inert and integrations fake.
6. Run the full repository suite and both review axes. Release code separately
   from any record/content migration. Remove owned proof copies afterward.

Repository tests alone do not establish installed Divi save/reopen or production
adoption. Record actual browser evidence before claiming those checks.

## Isolated installed-Divi verification, 29 October 2026

WordPress 7.1, Divi 5.11.0 and the current child theme ran in a separate local
Docker instance. Only synthetic event records and unpublished pages were used.
Mail and external HTTP were disabled. Shared staging and production received no
writes from this work.

| Native editor action | Result after Save, full reload and reopening |
| --- | --- |
| Enable include-Schnuppertage on the feed | Checkbox remains checked; the real query adds the synthetic visit beside the general event. |
| Set the feed limit to zero | Number control reopens as `0`; neither synthetic event renders. |
| Change the Schnuppertage event type to general | Selector reopens on general; the general event replaces the visit in the rendered list. |
| Save the feed with an unknown stored native attribute | The attribute remains byte-equivalent in the parsed block; known false/zero values remain typed. |

Published rows and their metadata had matching SHA-256 fingerprints before and
after the final save sequence. The check covered complete published post rows
and their metadata in the isolated database. Both proof pages, their revisions
and synthetic events were then removed, with a zero-remaining-record check.
Screenshots, snapshots and preservation/cleanup receipts are retained locally
under `output/issue-229-event-fields/`. This proves the installed editor workflow
in isolation; production adoption remains part of the separate code release.
